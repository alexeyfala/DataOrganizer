# Справочник по файлам решения

Назначение не-кодовых файлов решения: конфигурация сборки, правовые документы, шаблоны GitHub,
упаковка и документация. Исходный код, `.csproj` прикладных проектов и ресурсы приложения
(иконки, `.resx`) сюда не входят. Развёрнутые инструкции не пересказываются — на них стоят ссылки.

Порядок разделов повторяет дерево каталогов.

## Корень

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `.editorconfig` | Стиль кода и правила именования для всего решения. Вместе с `EnforceCodeStyleInBuild` из `Directory.Build.props` нарушения попадают в вывод компилятора, а не только в подсказки IDE. | Когда меняется соглашение об именовании или форматировании. Отдельная секция `[*.{csproj,wixproj,props,targets,wxs,wxi}]` удерживает табы в MSBuild- и WiX-файлах. |
| `.gitattributes` | Нормализация окончаний строк (`* text=auto`); остальное — закомментированные заготовки из шаблона Visual Studio. | Практически никогда — разве что git начнёт портить окончания строк в файлах нового типа. |
| `.gitignore` | Что не попадает в репозиторий: `bin/`, `obj/`, `.vs/`, `Publish/`, а также `Setup/LICENSE.rtf`. | Когда появляется новый генерируемый артефакт. |
| `Directory.Build.props` | Единственный источник версии и имён: `AppVersion`, `AppName`, `AppDisplayName`, `Manufacturer`, `License`, путь к иконке, имя MSI. Отсюда же берутся метаданные сборок (вкладка «Подробно» в проводнике) и включается `EnforceCodeStyleInBuild`. | Перед каждым релизом — поднять `AppVersion`. При смене имени продукта, автора или лицензии. |
| `DataOrganizerApp.slnx` | Решение в новом XML-формате: проекты, платформы и виртуальные папки (`Docs`, `Solution Items`, `Deployment`, `Tests`). WiX-проекты помечены `Build="false"`, поэтому обычная сборка решения их не трогает. | Когда добавляется проект или файл, который должен быть виден в обозревателе решений. |
| `README.md` | Витрина репозитория на GitHub: возможности, скриншоты, системные требования, сборка из исходников, размещение данных, лицензия. | При заметном изменении возможностей или требований. Скриншоты лежат в `Docs/Images/`. |
| `CODE_OF_CONDUCT.md` | Contributor Covenant; на него ссылается `CONTRIBUTING.md`. | Только при смене контакта для жалоб. |
| `CONTRIBUTING.md` | Как вносить вклад: способы участия, сборка, требования к pull request. | Когда меняется процесс работы с ветками или требования к PR. |
| `SECURITY.md` | Публичная политика безопасности: приватный канал через GitHub Security Advisories, состав отчёта, поддерживаемые версии, границы модели угроз. | Когда меняются гарантии шифрования или список поддерживаемых версий. Разметка блобов описана в `Docs/Encryption_Format.md`. |
| `LICENSE` | Полный текст Apache License 2.0. Единственная рукописная копия лицензии в репозитории. | Не править. |
| `NOTICE` | Уведомление, обязательное по Apache 2.0: копирайт, упоминание LGPL-компонента libuiohook, оговорка о названии продукта. | При смене года копирайта или появлении компонента с требованием об уведомлении. |
| `THIRD-PARTY-NOTICES.txt` | Список сторонних компонентов и их лицензий. Генерируется `tools/gen-third-party-notices.ps1` из графа NuGet-зависимостей; руками поддерживается только секция libuiohook. | Не править руками — перегенерировать перед релизом и закоммитить результат. |

Файлы `app.pupnet.conf` и `app.metainfo.xml` тоже лежат в корне, но описаны в разделе
[Deployment](#deployment).

## `.github/`

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `dependabot.yml` | Еженедельная проверка обновлений NuGet и GitHub Actions; minor и patch собираются в один pull request. | Когда обновлений от Dependabot становится слишком много или слишком мало. |
| `release.yml` | Категории и метки для кнопки «Generate release notes» на странице релиза. Метка `ignore-for-release` полностью прячет pull request. | При изменении набора меток репозитория. |
| `PULL_REQUEST_TEMPLATE.md` | Заготовка описания pull request с чек-листом. | Когда меняется чек-лист перед слиянием. |
| `ISSUE_TEMPLATE/bug_report.yml` | Форма отчёта об ошибке; issue получает метку `bug`. | При изменении набора обязательных полей. |
| `ISSUE_TEMPLATE/feature_request.yml` | Форма предложения; issue получает метку `enhancement`. | При изменении набора обязательных полей. |
| `ISSUE_TEMPLATE/config.yml` | Запрещает пустые issue и уводит вопросы в Discussions, а сообщения об уязвимостях — в приватную форму advisory. | При смене ссылок на Discussions или Security. |
| `workflows/ci.yml` | CI: сборка Desktop-проекта и прогон четырёх тестовых проектов на ubuntu, windows и macos при push и pull request в `master`. | Когда добавлен тестовый проект — его нужно дописать отдельным шагом. |

## `.vscode/`

Файлы для VS Code; Visual Studio их не читает. Имена и аргументы не повторяются в каждом файле:
`launch.json` и `tasks.json` берут их из `settings.json` через `${config:...}`. Согласованность
проверяет тест `VsCodeConfigConsistencyTests`.

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `settings.json` | Общие значения: `app.name`, аргументы сборки, скрытие `bin` и `obj` в дереве файлов. | При переименовании приложения — правится только здесь. |
| `tasks.json` | Задачи сборки `build-app` и `build-app-release`; на macOS собирается проект `.MacOS`. | При смене конфигураций или аргументов сборки. |
| `launch.json` | Конфигурации запуска Debug и Release; на macOS запускается `.app` из каталога сборки. | При смене целевой платформы или путей запуска. |

## Deployment

Три независимых пути упаковки: Windows — WiX (`Setup/` собирает `.msi`, `Bundle/` заворачивает его
в `.exe` вместе с рантаймом), Linux — PupNet (`app.pupnet.conf`). macOS собирается без отдельной
конфигурации, одними командами. Рецепты для всех платформ — [Publish.md](Publish.md).

### `Setup/` — установщик `.msi`

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `Setup.wixproj` | Проект WiX 7. В PreBuild генерирует `LICENSE.rtf` и публикует Desktop-проект, в PostBuild чистит `.wixpdb` и открывает папку с результатом. Выход — `Publish/DataOrganizer-<версия>-win-x64.msi`. | При смене платформы публикации или состава шагов сборки. |
| `Package.wxs` | Корень пакета: набор диалогов `WixUI_Advanced`, иконка в «Программах и компонентах», показ лицензии, единственная обязательная функция установки. | При изменении интерфейса установщика или метаданных пакета. |
| `Components.wxs` | Что именно ставится: `DataOrganizer.exe` как ключевой файл, всё остальное содержимое `Publish/**`, ярлыки в меню «Пуск» и на рабочем столе. | Когда меняется состав ярлыков или аргументы запуска. |
| `Folders.wxs` | Каталоги установки: `APPLICATIONFOLDER` и папка в меню «Пуск». | Почти никогда. |
| `Predefines.wxi` | Переменные препроцессора: имена, суффиксы `-Debug` и `-64bit`, `ProductComponentGUID` и `UpgradeCode`. | `UpgradeCode` после первой установки менять нельзя — иначе обновление поставит вторую копию программы рядом. |
| `IssueWorkaround.wxi` | Обход давнего дефекта `WixUI_Advanced`, ставившего 64-битную программу в `Program Files (x86)`. | Не трогать, пока дефект не исправят в WiX. |
| `LICENSE.rtf` | Лицензия для диалога установщика. Генерируется из корневого `LICENSE`, в репозиторий не попадает (`.gitignore`). | Не править — правится исходный `LICENSE`. |

### `Bundle/` — установщик вместе с рантаймом

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `Bundle.wixproj` | Burn-бандл. Перед сборкой сам собирает `Setup.wixproj`, после сборки удаляет из `Publish/` промежуточный `.msi`. Версия рантайма задаётся здесь (`DotNetVersion`), язык интерфейса — через `SetupCulture` из `Directory.Build.props`. | При переходе на новую версию .NET. |
| `Bundle.wxs` | Цепочка установки: поиск .NET 10 x64, при отсутствии — установка рантайма, затем вложенный `.msi`. Собственной лицензии у бандла нет, её показывает `.msi`. | При изменении состава цепочки. |
| `Localizations/HyperlinkTheme.en-us.wxl` | Строки интерфейса бандла на английском. | При правке текстов установщика. |
| `Localizations/HyperlinkTheme.ru-ru.wxl` | Строки интерфейса бандла на русском. Какой из файлов попадёт в сборку, решает `SetupCulture`. | При правке текстов установщика. |
| `Themes/HyperlinkTheme.xml` | Разметка окна бандла (тема `hyperlinkLicense` стандартного интерфейса Burn). | При изменении размеров окна или набора элементов. |
| `Resources/dotnet-runtime-10.0.11-win-x64.exe` | Официальный установщик рантайма (около 30 МБ), вшивается внутрь бандла, чтобы установка работала без интернета. | При переходе на новую версию .NET: скачать новый файл, обновить ссылку в `Bundle.wxs` и `DotNetVersion` в `Bundle.wixproj`, старый удалить. |

### PupNet — пакеты для Linux

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `app.pupnet.conf` | Конфигурация PupNet Deploy: идентификатор приложения, описание, лицензия, иконки, аргументы `dotnet publish`, настройки `.deb`, `.rpm`, AppImage, Flatpak и zip. Версия передаётся при сборке через `--app-version`, значение в файле — запасное. | При смене зависимостей пакетов, категорий или аргументов публикации. Пошаговые инструкции — [PupNet_Instructions](PupNet_Instructions/). |
| `app.metainfo.xml` | AppStream-метаданные для центров приложений (GNOME Software, KDE Discover). Большую часть полей подставляет PupNet макросами при сборке. | Руками заполняются только категории, ключевые слова, возрастной рейтинг и скриншоты — см. [3_AppStream.md](PupNet_Instructions/3_AppStream.md). |

## `tools/`

Скрипты PowerShell 5.1, запускаются из корня репозитория.

| Файл | Зачем нужен | Когда сюда лезть |
|---|---|---|
| `gen-license-rtf.ps1` | Заворачивает текстовый `LICENSE` в RTF для диалога установщика. | Запускается сам из PreBuild `Setup.wixproj`; вручную — почти никогда. |
| `gen-release-notes.ps1` | Подставляет версию из `Directory.Build.props` в шаблон описания релиза, пишет `Publish/release-notes.md` и копирует текст в буфер обмена. | При выпуске релиза, по шагам из `GitHub_Release.md`. |
| `gen-third-party-notices.ps1` | Пересобирает `THIRD-PARTY-NOTICES.txt` из `project.assets.json` распространяемого проекта. | Перед релизом и после изменения состава зависимостей. Требует свежего `dotnet restore`; в выводе нужно проверить отсутствие `UNKNOWN`. |

## Чего нет в репозитории

| Путь | Что это |
|---|---|
| `Publish/` | Готовые установщики, архивы и текст описания релиза. |
| `bin/`, `obj/` | Промежуточные результаты сборки проектов. |
| `.vs/` | Локальный кэш Visual Studio. |
| `Setup/LICENSE.rtf` | Лицензия для установщика, создаётся при сборке `Setup.wixproj`. |

## Кто кого читает

- `Directory.Build.props` → все проекты, `Setup.wixproj` и `Bundle.wixproj` (через `DefineConstants`), `gen-release-notes.ps1`, PupNet (через `--app-version`)
- `LICENSE` → `gen-license-rtf.ps1` → `Setup/LICENSE.rtf` → диалог лицензии в `.msi`
- `project.assets.json` → `gen-third-party-notices.ps1` → `THIRD-PARTY-NOTICES.txt`
- `Docs/release-notes.template.md` → `gen-release-notes.ps1` → `Publish/release-notes.md`
- `.vscode/settings.json` → `.vscode/launch.json`, `.vscode/tasks.json`
- `Setup.wixproj` → `Bundle.wixproj` (бандл сам собирает вложенный `.msi`)
